# 2026-10-22 移植方案：白屏根因重估与后续路线

基线 HEAD `c5290fb`。本文替代此前"查谁往影片池写 0xFF"的排查方向。

---

## 0. 一页结论

**白屏不是渲染缺陷，是 guest 逻辑线程挂起后的静止画面。** 本轮从 c122 的 `threads` 转储 + `main.patched.bin` 反汇编建立了新的证据链：
1. 白屏期间**没有任何 guest 线程在推进影片/装载状态机**：
   - 影片事件线程 `h=0x1025`：挂在 `svc 0x18 WaitSynchronization`，**等待句柄数 = 0**（`waiting on 0 handle(s)`），`last_svc=0x18`，`nsvc=105` 后不再动。它的调用链是 `nn::os::WaitAny(MultiWaitType*)`（`main+0xa68aa4`），前一条指令刚做完 `movie::MediaData::Clear/D1` 和一次 vtable+0x48 调用，返回值非 0 时走 `cbnz → 0xa68aa0` 重试循环；`0xa68aa8` 起把返回值与 `x21/x22/x23/[sp+0x10]/[sp+8]` 五个值逐一比较派发——**游戏代码自己就在处理 WaitAny 的多种非成功结果**。
   - 我们的 `runtime/threads.c:523` 对 `n==0` 的校验是 `(!hs&&n)` → 放行，然后 `block(t, 4, -1)` 把它挂进等待链，`wh[]` 为空 ⇒ **任何 signal 都扫不到它，永久挂起**。为什么真机不挂有两种候选解释（H-A 内核语义 / H-B 上游缺句柄，见 W0，本轮先取证再修）。
   - `ExecStartupShader` 线程 `h=0x1027`（线程名串 `0xf8bcca`，入口 `main+0x58fa10` 注册于线程表 `0xf3da28`）：卡在 `nn::os::AcquireSemaphore(task+0x38)`（`main+0x9a62a4`，GOT 槽 `0x12b6148` = `AcquireSemaphore`，反汇编确认）。**结构（subagent 反汇编全文核对）**：pump 函数 `main+0x9a6234` 把任务状态 `[task+0x28]` 置 3 → `ReleaseSemaphore(task+0x68)`（`0x9a629c`，唤醒 worker）→ `AcquireSemaphore(task+0x38)`（`0x9a62a4`，**等完成**）→ 返回后复查状态 `==5` 才跑完成回调。`Release(+0x38)` 的完成方站点在 `main+0x9a6af8/0x9a6bc8`（worker 收尾）。所以这条链是 core 装载体系的**消费半段**（等任务完成），不是此前文档说的"注册 bnk 那条链"（生产半段是 `0x58f7ec→0x8c9870→0x983b80→0x9974d4`，两者经同一任务池 `[0x12c7df0]` 耦合）。**影片线程挂 → 任务不完成 → `+0x38` 不归还 → 本线程永等 → 场景/着色器永不就绪。**
   - 主线程 `h=0x1001` 在 `h_nvnWindowAcquireTexture` 正常等上屏，每帧重放同一帧（`passdump` 的 2 次绘制 = 游戏每帧重画同一张 YUV 影片平面）。这解释了"帧号推进、30 fps、上屏正常、画面静止、md5 相同"。
2. **此前"池被填成 0xFF（白）"的证据无效**：`DM_NVN_UPLOG` 的 `nz8` 只统计"8 字节字非零"，而解码输出 Y=16..65 的填充字 `0x1010101010101010` 同样非零。"nz8=180800/180800" 与"池里是 0xFF"之间没有推理关系。屏幕呈近白 `(250,248,241)` 更可能是"平面停留在 EOS 后未被更新的状态 + 游戏 YUV 着色器把陈旧 UV 当有效数据合成"。
3. 音频混音恒 0（待办 2）与白屏**同源**：游戏逻辑没进会发声的状态，Wwise 自然混出静音。不要单独追。

**因此新的头号假设（W1）：修 `svc 0x18` 的 `count==0` 语义（立即返回错误而非永久挂起），影片线程恢复重试循环，白屏随之解除或暴露出下一层（EOS 后不重新 configure 第二部影片）。** 改动约 5 行，一轮 30 s 跑即可证伪。

## 3. 执行计划（每步一个可证伪假设，一轮只推进一条）

### W0（本轮，零行为改动）：`svc 0x18` 的句柄数轨迹——一次跑就区分 H-A / H-B
**两种解释必须先分叉，不要默认第一种**
- **H-A 宿主语义错**：真实内核对 `count==0` 立即返回错误、不挂起，游戏那条 `cmp x0,x22/x21/x23/[sp+0x10]/[sp+8]` 多值派发正是处理这些结果。我们的 `block(t,4,-1)` + 空 `wh[]` 让它谁都扫不到。
- **H-B 上游缺句柄**：`count==0` 只是症状——本该挂进 `MultiWaitType` 的某个事件句柄没进来。旁证：`h=0x1025` 的 `nsvc=105`（不是 1），说明它**之前正常等待过**（列表非空），后来才变空；而游戏事件循环是 `WaitAny → 按结果派发 → 调 vtable+0x48 取新事件（失败则 `cbnz → 0xa68aa0` 回 WaitAny）`，真机上若列表能变空就会变成忙循环，不合常理。**H-B 的先验不低于 H-A。**

**改动（只加诊断）**：`runtime/threads.c:523` `case 0x18` 入口加一个默认关的轨迹（`NIER_TRACE_SVC0=1`，范式照 `game_patches.c:nier_audio_state_tick()`：`getenv` 一次 + 行数封顶）：
1. **`n` 值变化时**打一行 `svc0x18 th=<tid> n <旧>→<新> x0=<MultiWait*> x1=<hs> x3=<timeout> last_svc=<#>`（上限 64 行）——回答"从几变 0、什么时候变 0"。
2. `n==0` 时额外 dump `x0` 指向对象的**前 48 字节 hex**（`nn::os::MultiWaitType = {lock; holder_list_head; count}`，用 `mach_vm_read_overwrite`，读不到打 `ok=0`，不会把探针自己搞崩——同 `game_patches.c` 的既有做法）。
3. 顺带记录该线程**前一次成功等待的句柄值**（`t->wh[]` 在 `n>0` 时已存，`n==0` 时打出来）——直接指出"是哪个句柄消失了"。
4. **同一开关下加第二个探针（同一轮拿齐证据）**：`game_patches.c` 里按 `nier_audio_state_tick()` 的现成范式，每 600 帧读一次任务池 `main+0x12c7df0` → `[+0x20]` 链（节点步长按 pump 反汇编 `0x9a6234` 系核对，先按 0xb0 试），统计各节点 `[+0x28]` 状态字分布打一行 `[taskpool] n=<链长> st3=<计数> st5=<计数> …`（上限 16 行）。判据：**大量 3 且无 5 ⇒ 等待方正常、完成方（worker/宿主 IO 回调）死**；有 5 在推进 ⇒ 任务系统活着，白屏另有原因。这同时覆盖 subagent 报告的观测建议 b/c。
- **判据（30 s 无导航）**：
  - `n` 从 ≥1 掉到 0 且掉的那一刻贴着影片 `end of stream` → **H-B**，转 W1b：查 `movie::Decoder::RegisterClientEvents` 的 4 个 EventType 与我们的事件生命周期（谁把 holder 摘了、EOS 后该不该摘）。
  - 全程 `n` 恒 0（该线程从来没等过真句柄）→ **H-A**，转 W1a：改 `n==0` 立即返回错误。
  - 探针没打出任何 `n` 变化（线程从头到尾只那一次 n=0）→ 说明它是在**第一次** WaitAny 就空列表，回到 W1a。
- **风险**：零（默认关、只读）。**回归**：`stability.sh 3 13` 必须 `STABLE`。

### W1a / W1b（按 W0 结论二选一，一轮只做一个）
- **W1a（H-A）**：`case 0x18` 加 `if (n == 0) { regs[0] = R_TIMEOUT; regs[1] = 0; return 1; }`。错误码不凭空造：先用现成的 `R_TIMEOUT=0xEA01`；若游戏分支不认，按 `main+0xa68aa8` 起的派发比较反推它期望值再做一次 A/B（最多两个候选，别试第三个）。
- **W1b（H-B）**：不改 svc，改影片事件的生命周期。取证点已现成：`h_register_events()`（`movie_host.c:299`）存了 4 个 `EventType*`；核对 EOS 后游戏是否期望其中某个仍可等待，以及我们的 `note()/fire()` 是否在某条路径上让 holder 被摘走。
- **共同判据**：`h=0x1025` 的 `nsvc` 持续增长；`wshot` 画面不再静止近白（md5 变化）；`ExecStartupShader`（`h=0x1027`）离开 `AcquireSemaphore(task+0x38)`；出现第二台解码器 `configured` 或 `stop/reset` 生命周期行。
- **风险**：W1a 低（只动 `n==0` 这条真机不允许的路径，`n>0` 分支一行未动）；W1b 中（改事件语义，需完整导航回归）。
- **回归**：`stability.sh 3 13` 必须 `STABLE`。

### W2：影片 EOS 之后的推进（W1 通了但序章影片仍不接力时做）
- 假设：游戏在 EOS 后需要"输出可用"事件驱动它走 `stop → configure(第二部) → start`；我们的 `h_acquire_output` 在 EOS 交付后返回 `ST_NO_OUTPUT` 是否让游戏状态机停在"等下一帧"。
- **取证优先**：`NIER_MOVIE_LOG=1` 长跑，记录 EOS 后游戏对解码器的**最后 5 次调用序列**（现在只打前 24 条生命周期事件，加"EOS 后仍打"的小尾巴，上限 40 行）。对照 `docs` 内 MediaCodec 语义（`movie_host.c` 头注释）。
- 判据：第二部影片 `configured` 行出现，或明确证伪（EOS 后游戏确实不再调解码器 → 转查上层影片播放器状态机）。

### W3：每帧新建 1728 KB 纹理（独立缺陷，独立提交，可与 W1 并行准备）
- **改动**：`nvn_mtl.m:3303` `REUP_MAX_BYTES` 1 MB → 4 MB。审计已确认：复用键只含描述符、无内容哈希，但 `pkg_upload_` 每次**全量覆写**所有 level×layer，复用不会读到旧内容；唯一例外是 cube-array 截断路径（影片平面不是 cube array，不受影响）。风险上限 = 缓存 256 槽 × 4 MB 的滞留，`REUP_IDLE=600` 提交后退。
- **实测判据**：白屏修复后的长跑里 `[tex-new] … 1600x904` 行从"每帧 1 次"降到接近 0；`显卡已分配` 不再随帧线性涨。
- **回归**：`stability.sh 3 13`；另跑一轮 `TOTK_REUP_RECYCLE=0` 对照确认开关仍有效。

### W4：`DM_NVN_UPLOG` 统计修正（防再次误判，改动极小）
- 在现有块（`nvn_mtl.m:3372-3376`）把 nz8 升级为单遍字节统计：`bmin/bmax/bmean`、`0xFF 字节占比`、前 16 字节 hex。默认关不变、行数上限不变。
- 判据：对同一轮 `1600x904` 上传能直接读出"是 0xFF 填充还是图像"，不再靠非零字推断。

### 执行顺序与节奏
W0（取证，零行为）→ W1a 或 W1b（按 W0 结论二选一）→（若影片仍不接力）W2 → W3（随时可独立提交）→ W4（搭 W3 的车）。每轮：`pgrep -fl "nier-native|logs/c"` 确认干净 → 改 `runtime/*.c` 必 `touch` → make（约 9 s）→ 30 s 无导航冒烟 → 225 s 导航长跑 → `stability.sh 3 13` → 独立提交 + CHANGELOG 实测数字。

## 6. 工程纪律（针对"跑半天没进度 + 各种回归"）

1. **一轮一个假设、一条实测数字**，写进 CHANGELOG（含被证伪的），禁止一轮改两处行为。
2. **先全局仪器后单点猜测**：本轮的突破口是 `threads` 转储（现成命令）+ 反汇编 GOT 符号化（`runtime-layout.json` 的 relocs 表把 `bl stub` 还原成 `AcquireSemaphore/WaitAny`）。把"线程等待图"固化为每轮长跑的标配输出（脚本尾部加 `threads`）。
3. 证据链检查：每条"→"结论要问"这个统计/日志能区分几种假设？"（nz8 教训：非零字计数区分不了 0xFF 与图像）。
4. 环境坑清单维持（touch、单实例、pkill 自伤、`sed` 派生脚本校验、worktree 覆盖 build）。
5. svc 语义层回归面：`threads.c` 每次改动必须跑 `stability.sh 3 13` + 一轮完整导航（音频、装载、影片三段都过）。
