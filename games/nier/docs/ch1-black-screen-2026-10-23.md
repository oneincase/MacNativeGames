# 第一章节黑场诊断（2026-10-23，无人值守轮次）

## 结论

**未修复。** 已把范围压缩到「场景 HDR RT 本身是 0」，但没找到把它写成 0 的环节。

## 已确认的事实

1. **场景 RT 是 0**：`c283` 黑场景帧 2600 抓到 `td_16.png.raw`（ser=16，1920x1080 RG11B10F）解码 `linear mean=0, max=0`；`td_19.png.raw`（tonemap 后）同样全 0。→ 不是 tonemap、不是上屏、不是偏色问题。
2. **写 16/17 的 pass 有 5 个，几何照常提交**（`c294` 帧 3934）：`vc=966/36/1044/4/1056`，`wm=0xffff000f`，`tgt=1920x1080`。→ 不是「没画」。
3. **写这些 pass 的 FS 共 8 个**：`0ff2b337`、`57290de6`、`3b3b433a`、`49bd7a78`、`480167c6`、`fd2c47b7`、`9652ad6f`、`72a5eb8f`。
4. **单独把其中几个的输出改红无效**：`0ff2b337`（c295，亮度 41.2→41.2）、`57290de6`（41.0）、`3b3b433a`（40.9），都与基线 41.1 无差别。→ 改输出这条路没有命中真正的写者，或者命中了但被后处理覆盖。
5. **批量把 8 个 FS 的 x/y/z 全改红会崩**（c296 帧 600），说明它们之间有时序依赖，不能一起改。
6. **`0ff2b337` 的 irradiance 极小**：`c288` 分通道探测得到 `_1531 ≈ 4.2`，而 shader 要求 `sqrt(_1531) > 6`（即 `_1531 > 36`）才不黑，差 8.6 倍。这是「暗」的机制，但**没有证据表明它是「黑」的唯一原因**——因为改它的输出没有可观测效果。
7. **排除**：mip（`level(5.0)→level(0.0)` 无变化）、贴图格式（`0x8b` → ASTC 6x6 sRGB，映射正确）、GS（passthrough，顶点直通）。

## 当前过渡措施

`app/launcher.m` 的 `NIER_GAMMA` 从 0.6 压到 0.45（提交 `a6e916e`）。效果：黑场景亮度 24.6 → 41.1，背景和 UI 可见，**但 3D 世界仍然是黑的**。这不是修复。

## 下一轮建议

1. 抓黑场景的 `DM_NVN_TEXRAW=17,19`（帧 3900 后稳定期），确认 17 是否也是 0——如果 17 非 0 而 19 是 0，问题在 tonemap；如果 17 也是 0，问题在写 17 的 5 个 pass。
2. 用 `DM_NVN_PASSDUMP_ALL=1` 看这几个 pass 的 `load`/`clear` 语义与 `rp_begin_ex` 的 `preaux` 路径，确认不是「画到暂存块再被丢弃」。
3. 逐个 FS 改红时不要碰 `.w`，且必须在同一帧窗口（先 `passdump` 定位帧号，再用该帧跑）。
