# 第一章节黑场诊断（2026-10-23，无人值守轮次）

## 结论

**未修复。** 已把范围压缩到「场景 HDR RT 本身是 0」，但没找到把它写成 0 的环节。

## 已确认的事实

1. **场景 RT 是 0**：`c283` 黑场景帧 2600 抓到 `td_16.png.raw`（ser=16，1920x1080 RG11B10F）解码 `linear mean=0, max=0`；`td_19.png.raw`（tonemap 后）同样全 0。→ 不是 tonemap、不是上屏、不是偏色问题。
2. **写 16/17 的 pass 有 5 个，几何照常提交**（`c294` 帧 3934）：`vc=966/36/1044/4/1056`，`wm=0xffff000f`，`tgt=1920x1080`。→ 不是「没画」。
3. **写这些 pass 的 FS 共 8 个**：`0ff2b337`、`57290de6`、`3b3b433a`、`49bd7a78`、`480167c6`、`fd2c47b7`、`9652ad6f`、`72a5eb8f`。
4. **单独把其中几个的输出改红无效**：`0ff2b337`（c295，亮度 41.2→41.2）、`57290de6`（41.0）、`3b3b433a`（40.9），都与基线 41.1 无差别。→ 改输出这条路没有命中真正的写者，或者命中了但被后处理覆盖。
5. **批量把 8 个 FS 的 x/y/z 全改红会崩**（c296 帧 600），说明它们之间有时序依赖，不能一起改。
6. **`0ff2b337` 的 irradiance 极小**：`c288` 分通道探测得到 `_1531 ≈ 4.2`，而 shader 要求 `sqrt(_1531) > 6`（即 `_1531 > 36`）才不黑，差 8.6 倍。这是「暗」的机制，但**没有证据表明它是「黑」的唯一原因**——因为改它的输出没有可观测效果。
7. **排除**：mip（`level(5.0)→level(0.0)` 无变化）、贴图格式（`0x8b` → ASTC 6x6 sRGB，映射正确）、GS（passthrough，顶点直通）。

## 当前过渡措施

`app/launcher.m` 的 `NIER_GAMMA` 从 0.6 压到 0.45（提交 `a6e916e`）。效果：黑场景亮度 24.6 → 41.1，背景和 UI 可见，**但 3D 世界仍然是黑的**。这不是修复。

## 下一轮建议

1. 抓黑场景的 `DM_NVN_TEXRAW=17,19`（帧 3900 后稳定期），确认 17 是否也是 0——如果 17 非 0 而 19 是 0，问题在 tonemap；如果 17 也是 0，问题在写 17 的 5 个 pass。
2. 用 `DM_NVN_PASSDUMP_ALL=1` 看这几个 pass 的 `load`/`clear` 语义与 `rp_begin_ex` 的 `preaux` 路径，确认不是「画到暂存块再被丢弃」。
3. 逐个 FS 改红时不要碰 `.w`，且必须在同一帧窗口（先 `passdump` 定位帧号，再用该帧跑）。

## 第二轮补充（同日 17:30–18:15）

### 新证据

1. **三个缓冲都抓到了**（`c298`，帧 3800，黑场景）：
   - `td_16.png.raw`：linear mean 0.0003/0.0002/0.0001，**max 2.531/1.766/1.125**
   - `td_17.png.raw`：linear mean 0.0003/0.0002/0.0001，**max 2.500/1.734/1.094**
   - `td_19.png.raw`：linear mean 0.0041/0.0120/0.0474，**max 0.984/0.969/0.938**
   - → 16/17 不是全 0，**有极少数高亮点**；19 是这些亮点经 tonemap 的结果。
2. **`td_1700.png`（17 的全屏采样）看清了亮点是什么**：黑底上只有一个金色光环（2B 的武器/机能光效）和两颗小点。→ **场景几何画了，但只有自发光部分可见，受光的部分（身体、地面）是黑的。** 这和用户说的「人物模型都是黑的」完全一致。
3. **8 个写 16/17 的 render pass FS 逐个改红全部无效**：`0ff2b337`、`57290de6`、`3b3b433a`、`49bd7a78`、`480167c6`、`fd2c47b7`、`9652ad6f`、`72a5eb8f` 改完亮度都是 40.9–41.2（基线 41.1）。**→ 17 的内容不是这些 render pass 写出来的。**
4. **同帧有 5 个 compute dispatch**（`c294` 的 `C` 行：`f897d9ae` 30x17、`e7a8b3a1` 60x34、`4072f08f` 2x2x8、`9be04df0` 13x7、`13fb7b74` 1x1）。**`dispatch()` 的 passdump 只记 storage buffer（`S.ssbo`），不记 storage texture** → compute 写了什么纹理目前不可见。

### 修正上一轮的判断

`0ff2b337` 的 irradiance（`_1531≈4.2`）确实是「暗」的机制，但**它不是「黑」的写者**——改它输出无效。上一轮把它当根因是过度推断，撤回。

### 下一轮唯一该做的

给 `dispatch()` 的 passdump 补上 storage texture 的记录（`nvn_mtl.m:10959` 一带，`C` 行加 `img` 列表），然后重跑一次黑场景，看这 5 个 compute 里哪个写 ser=16/17。如果是 compute，那 `rp_begin_ex` 的 `gpu_owned_mark` 与回写路径也要跟着检查（compute 写完的纹理不能被当 guest 内容重传覆盖）。

## 第三轮补充（同日 18:00–19:10）

### 新证据

1. **compute 不写纹理**：给 `dispatch()` 的 passdump 补了 storage image 记录（`S.img[5][i]` 的 ser），重跑黑场景（`c300`，帧 3866）——**5 个 dispatch 的 `i%d` 全部为空**，它们只写 storage buffer（`s0..s7`）。→ compute 不是写 ser=16/17 的人。
2. **没有纹理拷贝写 16/17**：同帧 719 条 `X/Y/U/E` 全是 buffer 拷贝/更新（`copy_b2b`/`update_ub`/`update`），没有 `copyFromTexture` 到 16/17。
3. **irradiance 贴图抓不到**：`1056807E` 对应 reg12 = ser3982（32x32），`DM_NVN_TEXPNG=3982` 报「不在序号表」→ 它不是通过 `nvnTextureInitialize` 创建的（可能是直接 Metal 纹理或跨 serial 共享）。`ser=1645`（16x16 cube array，341 层）和 `ser=103`（960x540）能抓到。
4. **8 个 render pass FS 改红仍然无效**（见第二轮），而 passdump 确认这 5 个 pass 就是唯一写 16/17 的 render pass。

### 现在的矛盾

- render pass 是唯一可能的写者，但改它们的最终输出无效；
- compute 和拷贝都排除了；
- 16/17 里有亮点（2B 光环），说明写入确实发生。

**最可能的解释：我改的 MSL 不是运行时实际编译的那一份。** `rt-totk-native-v4-unverified/` 下同一个 key 可能存在多个变体（`-<hash>_b`），而 `probe` 脚本用 `ls | head -1` 只改第一个。需要先确认运行日志里到底加载了哪个变体（`TOTK_KEEP_MSL=1` 或打印 key）。

### 修正

上一轮说「8 个 FS 不是写者」下得太早——应该是「改它们的输出没有可观测效果」，原因可能是改错了文件，而不是它们不写。

## 第四轮（同日 21:30–22:15）：找到真正的写者

### 关键突破

用 `passdump 1` 在**黑场景现场**（F3912）转储，写 ser=17 的最后一个 pass 是 `140663`，挂了 4 个此前从未试过的 FS：

```
pass 140663:
  vs=3c031497 fs=5aa81f6b   (227 行)
  vs=5f880399 fs=66ba9531   (体积雾)
  vs=5f880399 fs=8166d5ef   (124 行)
  vs=5f880399 fs=ac309751   (109 行)
```

把这 4 个的输出改成红色（`c317`）：

| 批次 | 改动 | 亮度 | mean(R,G,B) |
|---|---|---|---|
| c294 基线 | — | 41.2 | 16.3 / 24.8 / 45.9 |
| c305 | `9652ad6f` 红+alpha1 | 40.9 | 28.7 / 41.7 / 68.7 |
| c313 | `0ff2b337` slice=0 | 40.8 | 28.6 / 41.7 / 68.7 |
| **c317** | **这 4 个改红** | **53.9** | **56.6 / 50.8 / 76.0** |

**R 16.3→56.6、亮度 41.2→53.9、≥60 占比 4.7%→18.1%** → 改动生效，这 4 个才是最终写者。

### 为什么之前 8 个 FS 全无反馈

`140663` 是**最后一个**写 ser=17 的 pass，它读场景 RT 并输出最终画面；之前改的 `0ff2b337`/`9652ad6f` 等都在它之前，写的内容被它整体覆盖。passdump 里「5 个 pass 写 17」是对的，但只有最后那个的结果留下。

### 这 4 个 FS 的角色

`8166d5ef`（124 行）是核心：

```glsl
float4 bloom = sample(1056805A, uv_bloom);
float sceneAlpha = sample(1057805E, uv_scene).w;
float mixW = fma(d, alpha*(1-alpha), alpha*alpha);
float a = clamp(fma(sceneAlpha, mixW, ...) * in.w, 0, 1);
if (a <= threshold) discard_fragment();
out.rgb = mix(bloom.rgb, ...) * ...;
out.w = a;
```

把 bloom 以 alpha 混合叠到屏幕。`5aa81f6b`、`ac309751` 也读 `1056805A`（bloom），`66ba9531` 是体积雾。

**输出接近 0 的两种可能**：bloom 是黑的，或 `sceneAlpha`/`mixW` 算成 0 导致整片 `discard_fragment()`。

### 下一步

抓 `1056805A`（bloom）在黑场景的实际内容，并看 `1057805E` 的 alpha 通道。两者定性后即可定位。

### 工具说明

新增两个默认关的诊断（`nvn_mtl.m`）：
- `NIER_PASS_TRACE=1`：在 `rp_end` 打出本 pass 的全部颜色附件 serial + draws 数（绕开 passdump 的自增 pass 号）
- `NIER_SHADER_TRACE=1`：打印实际加载的 MSL 变体名与源码长度（`prebuilt=` 表示是否走了预编译库）
