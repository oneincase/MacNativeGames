## 0. 一句话结论

渲染/影片/音频/存档链都已打通并进到序章飞行场景，但**当前挡住"能玩下去"的不是偏色，是显存预算主动中止**：

- **闪退（P0-A，最高优先）**：**第一因是 GS 捕获缓冲扩容时旧缓冲被立即释放 → GPU 裸地址页故障**（帧 2175/83 s，`kIOGPUCommandBufferCallbackErrorPageFault`），GPU recovery 之后失败提交占用的显存不再回收，`currentAllocatedSize` 从 2312 MB 一路涨到 10916 MB，安全阀 `gpu_budget_check` 才 `abort()`（`$WORK/logs/c184.log:4153`）。已被连带误记为"纹理缓存 113 个 66 MB = 7458 MB"，实为 113 个共 66 MB。修法见 §2.3，1 行延迟释放。
- **偏色（P0-B）**：真值对齐后确认是"后处理链把 G/R 从 1.22 推到 1.85"，不是输入数据错。详见 §1。
- **GS 默认路径（P1）**：默认丢弃 stage-2，世界几何不出画。
- **序章之后（P2）**：零验证，且需要存档——而存档要等 P0-A 修好。

## 2. 闪退根因（P0-A）

### 2.1 证据链（全部可复现）

- 崩溃报告 `~/Library/Logs/DiagnosticReports/nier-native-2026-10-22-181640.ips`：`EXC_BAD_ACCESS/SIGABRT`，`asi: abort() called`，faulting thread #5 栈为 `gpu_budget_check +396`（`nvn_mtl.m:297-307` 的 `MDIE`）。
- 同一时刻日志 `$WORK/logs/c184.log:4153`：`显卡已分配 10916 MB（零拷贝 guest 池 1913 MB，实际 9003 MB）超过预算 9000 MB`。
- **增长不在驻留集里**：常驻明细 `c184.log:4140` 是 `113 个 66 MB`＝**113 个对象、合计 66 MB**（0.58 MB/张，普通小纹理），整个驻留集合计 1781 MB，从帧 900 到崩溃前只涨了 89 MB。纹理缓存不是增长源。
- `NIER_ALLOC_TRACE=1`（c191）逐帧拆分：帧 40→1639，显卡 2041→2303 MB，未登记 60→84 MB，零拷贝池 1831→1909 MB，全程平稳。**正常状态下不涨**。
- **真正的第一错在帧 2175（83.08 s，标题画面）**：`[gs] 捕获绘制：非索引 0 次 / 索引 4097 次（本帧顶点 2310）` 之后紧跟 `【红】分段命令缓冲错误 fence=2191：kIOGPUCommandBufferCallbackErrorPageFault`（`Caused GPU Address Fault Error`）。
- 紧跟其后的 `GS 绑定核对` 40 条全部回查为 `池在`（guest 地址都还在映射池里）——**页故障来自宿主裸 GPU 地址，不是 guest 地址失效**。
- 之后 GPU 进入 recovery：`InnocentVictim`（fence=2191）、`SubmissionsIgnored`（帧 2639–2642，每帧 2 张贴图重传被丢）……直到 `gpu_budget_check` abort。
- 显存时间线：帧 2100 = 2312 MB（正常）→ 帧 2400 = 6240 MB → 崩溃前 10916 MB。**拐点正好在帧 2191 页故障之后**。

### 2.2 机制（根因）

`nvn_mtl.m:6466-6471`（修复前）GS 压缩的捕获缓冲按程序 VS 扩容：

```objc
id<MTLBuffer> capb = bufs[bk];
if (!capb || capb.length < capn * 64) {
    capb = [g_dev newBufferWithLength:capn * 64 options:...];   // 新缓冲
    res_add(capb); bufs[bk] = capb;                             // 字典覆盖 → 旧缓冲最后一个强引用消失
}
```

进入标题画面时同一个 VS 连续扩容 `3072 KB → 3584 KB → 3840 KB` 三次，**每次旧缓冲立刻 dealloc**；而前面几个提交里的捕获 pass（GPU 渲染命令）与压缩内核还在按裸地址读写它 → `kIOGPUCommandBufferCallbackErrorPageFault`。GPU recovery 之后，失败提交占用的资源不再回收，`currentAllocatedSize` 一路涨到预算，安全阀 `gpu_budget_check` 才 abort —— **闪退是页故障的下游，不是纹理缓存无上限**。

同文件的上传路径 `g_up_pblock`（`:3218-3220`）早就用 `defer_obj_release` 处理了同一模式，捕获缓冲漏了这一步。

### 2.3 修法（已实施 + 待做）

1. **【已改，L2 小改】捕获缓冲扩容时延迟退役旧缓冲**：新建后 `if (capb) defer_obj_release(capb);`，再换字典。旧缓冲保留在驻留集里，等用到它的提交全部完成（`d->fence <= g_done`）才撤驻留并释放。
2. **【待做】同类模式全库审计**：任何 `x = [g_dev newBuffer/Texture...]` 覆盖旧值的地方都要走 `defer_obj_release`；已确认 `g_vis_ring[pick].buf`（`:1074`）只创建一次、`g_parb`（`:6517`）固定尺寸不重建，无需改。
3. **【待做】页故障可观测**：给 GPU 错误回调加一条 `[gpu-fault]` 计数与首个帧号，避免下次再从 `MTL4CommandQueueErrorDomain` 文本里捞。
4. **【待做，按需】预算分级降级**：超预算先跑一轮淘汰再复检，仍超才 abort；预算默认改 `hw.memsize` 的 55%（`TOTK_GPU_BUDGET_MB` 可覆盖，launcher 不再硬编码 5000）。

### 2.4 判据（P0-A 完成）

- 复现同样的导航（35 s 起标题、~230 s 进飞行场景），跑到 400 s：**0 次 `PageFault` / `InnocentVictim` / `SubmissionsIgnored`**；
- `显卡已分配` 峰值不再单调上升：帧 2100 与帧 2400 都在 2.3–2.6 GB 量级；
- 0 次 `gpu_budget_check` abort；预算按 9000 MB（复现崩溃时的配置）跑通，再按 5000 MB（launcher 配置）跑通。

## 3. 偏色（P0-B）：作战计划

前置：P0-A 修好前不要跑长程 dump（越玩越容易撞预算，dump 本身还会加剧）。

### 3.1 一次判决跑（零改动）
```
TOTK_GPU_BUDGET_MB=<按 §2.3 调高> DM_NVN_PASSDUMP=<飞行场景帧-2..+2> \
DM_NVN_TEXPNG=16,19,21,24,25,26,34,84 DM_NVN_TEXRAW=19 \
DM_NVN_UPLOG=1920x1080 DM_NVN_LIFELOG=1920x1080
```
产出 `ser=19` 的**唯一写入者**（由 `[pass]` 序列判定），把"ser=16 → ser=19"之间的 pass 列成候选。

### 3.2 已证实的现象（2026-10-23，`DM_NVN_RTPROBE`）
`ser=84`（bloom 链 50x28 级）在**写入 pass 刚结束时**读回是**暖色**：
- `F8400 p327010`（83→84 四抽平均）`mean=1364.0,1072.5,675.1`（R>G>B，暖）；
- `F8400 p327016`（90→84 composite）`mean=2016.0,1171.2,1008.0`（R 已饱和到 11 位上限）。

但同一帧末 `texdump` 读到的 `ser=84` 是 **mean=(0,255,0) 纯绿**。→ **绿不是 shader 写进去的，而是写入之后被另一条非 shader 路径覆盖。** shader（`af6be82a…` 四抽平均、`7b61c45a…` 16-tap 高斯加权）与常量（`cb2` 四通道同权重 `0.3071/0.0002/0.0011/0.0052`）均已逐字节核对为正确。

序列：`376210`(83→84 平均，RTPROBE 暖) → `376254`(84→90) → `376257`(90→84 composite，RTPROBE 暖) → **帧末 texdump 纯绿**。候选覆盖者：`wb_level_back`（GPU→guest 回写）、`mtl_pool_invalidate` 后的重传、`blk_copy`（块渲染回写）、`up_flush`（上传 blit）。判决：`DM_NVN_TILELOG=50x28`（c198）。

### 3.3 假设与判决
- **H1｜后处理 pass 的变换把色相推绿**：逐个 `skipfs_<key>` 跳过候选 pass，看哪一个跳过能让 ser=19 的 G/R 回到 1.2 且画面结构完整。最可能命中 tonemap / 色彩矩阵 / bloom 合成。
- **H2｜bloom 被 compute/t2t 写后遭 guest 重传覆盖**：`OP_DISPATCH`/`OP_COPY_T2T`/`OP_CLEAR_TEX` 都**不**标 `gpu_owned_mark`（全文只有 `rp_begin_ex:4542-4543`），被 compute 写过的缓冲可能被 guest 旧字节重传。判决：同帧 `TEXPNG`+`TEXRAW` 对比 Metal 侧与 guest 侧统计；不一致即确认。修法为 L1 补标记，但必须先在 L2 门后验证"该重传的不漏"。
- **H3｜下游 view 格式错**（11B10F 被按 16F/R32F 读）：`PASSDUMP_ALL` 查该 pass 绑定的 view 格式。
- **H4｜B 偏低另有来源**（ser=16 已 1.34）：查 bloom/曝光是否按通道加权；量级小，排在 H1 之后。

### 3.4 判据（P0-B 完成）
同一帧画面的 **G/R 落进 1.00–1.25、G/B 落进 0.90–1.10**（对照 §1 真值表），且保留橙色引擎光；用户目视确认。
